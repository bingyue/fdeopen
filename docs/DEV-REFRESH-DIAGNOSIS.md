# 开发环境反复刷新排查（2026-10-20）

## 处理结论

项目使用 Next.js 16.4.0。现已在 `next.config.ts` 关闭
`experimental.turbopackFileSystemCacheForDev`，阻断跨进程恢复开发缓存的已知异常路径。
会话内 Fast Refresh、生产构建缓存、业务数据与权限保持原有行为。每次启动开发服务后首次访问页面需要重新编译。

这是针对已知框架回归的项目侧规避配置，不是修改 Next.js 内部代码。
**旧故障在本次受控测试中未再次出现，不能把上游相似问题当作原故障已经完全确诊。**
不要据此宣称消除了所有内存泄漏；开发态内存保留仍有单独记录。

## 证据与代码检查

- 2026-10-19 保存的 trace：约 123.68 秒内 352 次首页渲染、679 次 HMR 耗时事件，更新模块列表均为空；JS 堆由约 157.3 MiB 增至 1528.1 MiB。期间发生过回收。
- 原异常启动先请求 `/api/health`，随后开始重复首页渲染。
- 检查首页、导航、客户端副作用、请求工具和数据库初始化：未发现首页轮询、自动 `router.refresh()` 循环；刷新调用位于用户提交成功后的处理函数。数据库由 `globalThis.fdeDb` 保存初始化 Promise，没有每次渲染新建连接。
- 浏览器扩展注入的 `mpa-*` 属性只能解释对应的 hydration 属性警告，不能单独解释持续重载。没有隐藏 hydration 警告、关闭安全响应头或删除数据库。
- 安装版 Next 的 `server/dev/hot-reloader-turbopack.js` 会转发订阅初始非 issues 消息，并在客户端 HMR 版本不匹配时发送 `RELOAD_PAGE`。上游报告记录了恢复开发磁盘缓存后持续收到 `restart` 的循环，关闭该缓存可以避开。

参考：[Next.js #100251](https://github.com/vercel/next.js/issues/100251)、
[#100267](https://github.com/vercel/next.js/issues/100267)。配置语义也已核对本地随安装版分发的
`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/turbopackFileSystemCache.md`。

## 验证方法

使用独立的本地 3218 端口、隔离演示数据库 `.data/refresh-debug/db`、无扩展 Playwright 浏览器。
每次诊断服务器最多运行 240 秒，Node JS 堆限制为 1024 MiB。没有操作原业务数据库。

1. 分别测试页面优先、健康检查优先启动；在浏览器内切换页面，再保持页面打开重启开发服务器。
2. 预热 22 个媒体和社区页面，记录主文档请求、RSC 请求、HMR `restart`、版本不匹配、运行时错误。
3. 临时修改首页一句文字，等待浏览器出现新文字，随后恢复文件并比对原始字节。
4. 内存对照：页面预热后强制 GC 取基线，连续执行三组各 20 次首页 HTTP 请求，再空闲 45 秒并 GC。开发与生产使用相同数据和请求方式。
5. lint、TypeScript、生产构建及运行验证；结束后停止所有本次服务器与测试浏览器。

临时诊断代码不会加入应用启动流程，生产应用没有强制 GC 或定时内存采样。

## 已验证结果

- 修改前的多轮受控重启未再次出现旧循环；因此没有“修复前必现、修复后不现”的完整本地因果对照。
- 配置修改后的页面访问和重启检查未发现循环 `restart` 或 HMR 版本不匹配。
- 最终配置连续两轮重启（含一次 `NEXT_PUBLIC_SITE_URL` 变化）：每轮观察 30 秒，各 1 次正常重连后的整页加载，0 次循环 `restart`、0 次版本不匹配、0 个运行时错误。
- 正常热更新验证：文字即时改变，1 次 RSC 请求、0 次整页加载、0 个运行时错误，文档 timeOrigin 保持一致；临时文字已恢复。
- 页面预热：22 个公开页面全部返回 HTTP 200。
- lint、类型检查与生产构建通过。

### 内存判断边界

连续无 JavaScript 的 HTTP 请求会产生与真实浏览器不同的开发调试数据生命周期。
开发模式下 60 次请求后，即使空闲并 GC，仍观察到堆保留增长。
Next 内部独立调试通道的等待队列没有超时清理，但关闭 `reactDebugChannel` 的对照没有明显改善增量，
因此已撤回该实验性修改，未把它当作已定位或已修复的内存根因。

同量请求对照的回收后 JS 堆如下（MiB；RSS 是另一指标，不能与堆相加）：

| 环境                                    | 预热后基线 | 60 次请求后 | 再空闲 45 秒后 |
| --------------------------------------- | ---------: | ----------: | -------------: |
| 最终开发配置                            |     237.82 |      291.63 |         264.57 |
| 临时关闭 debug channel 的对照（已撤回） |     227.99 |      278.29 |         255.41 |
| 生产构建                                |      58.27 |       58.46 |          58.41 |

所有请求均返回 200。生产对照没有出现相同幅度的堆保留增长；开发态仍需区分框架缓存、调试数据与真正泄漏。
这次没有完成堆对象保留链分析，短期请求对照也不能证明长期运行不存在泄漏。
生产浏览器中的部分 RSC 预取在导航时被取消，不属于页面重复加载或运行时异常。

诊断进程和测试浏览器已经停止，原本的 3215 端口没有重新启动；3218、3219 也没有保留服务。

## 后续升级时的回归步骤

1. 在隔离测试环境临时恢复开发磁盘缓存，启动服务，在不同页面间做客户端跳转；保留浏览器标签页和 `.next/dev/cache`，停止服务。
2. 重启服务，让 `/api/health` 成为首个请求，再观察页面至少 30 秒；重复数次，并覆盖 `NEXT_PUBLIC_*` 配置变化。
3. 正常重连允许一次整页刷新；持续页面加载、重复 `restart`、`HMR hash mismatch` 均判失败。
4. 修改并恢复一处页面文字，确认正常 Fast Refresh 仍能工作。
5. 只有在目标 Next 版本通过上述验证后，才考虑恢复开发磁盘缓存。
